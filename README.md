# cinder-mcp

An MCP (Model Context Protocol) server that exposes
[cinder](https://github.com/muhammadrashid4587/cinder) — a Redis-compatible
key-value store in C — as tools for AI agents.

## What it is

A bridge. It speaks MCP (JSON-RPC 2.0 over stdio) on one side and cinder's
RESP protocol over a plain socket on the other, so an agent that can call
MCP tools can read and write a cinder instance. Pure Python 3 standard
library, zero dependencies.

## What it is not

It is not a database. It stores nothing itself. It requires a running
cinder instance, and if cinder is not reachable every tool call fails
with a clean JSON-RPC error instead of silently returning nothing.

## Setup

```sh
# 1. Start cinder (from the cinder repo, default port 6379)
./cinder --port 6379 --data-dir ./data

# 2. Run this server (it connects to cinder on 127.0.0.1:6379 by default)
python3 -m cinder_mcp.server

# Or point it elsewhere:
CINDER_HOST=127.0.0.1 CINDER_PORT=6380 python3 -m cinder_mcp.server
```

Wire it into an MCP client as a stdio server with the command
`python3 -m cinder_mcp.server` and the working directory set to this repo.

## Latency budgets

Every tool has a latency budget: a warn threshold and a slow threshold
in milliseconds. Defaults are 100ms warn / 500ms slow; override them
with environment variables:

```sh
CINDER_MCP_WARN_MS=50 CINDER_MCP_SLOW_MS=200 python3 -m cinder_mcp.server

# Per-tool overrides as JSON (partial overrides inherit the defaults):
CINDER_MCP_BUDGETS='{"kv_keys": {"warn_ms": 250, "slow_ms": 1000}}' python3 -m cinder_mcp.server
```

A tool whose p95 latency is over its warn threshold is flagged `warn`
in `cinder://metrics`; over its slow threshold it is `slow`. The
metrics resource also counts, per tool, how many individual samples
crossed each threshold, and `cinder://info` ends with a summary line
listing the tools currently over each threshold. A misconfigured
budget (non-numeric, non-positive, or slow at or below warn) fails
the server at startup instead of running with nonsense thresholds.

Each tool's budget is also advertised up front: `tools/list` appends
"Latency budget: warn >100ms, slow >500ms." (or the tool's override
values) to the tool's description, so a client knows the budget
before calling.

A single call that crosses its own budget is also flagged inline, in
the moment: the `tools/call` result carries a `warning` field with
the level (`warn` or `slow`), the tool, the measured latency and the
threshold it crossed, so the client sees it without polling
`cinder://metrics`. Calls within budget carry no `warning` field.

## Tools

| Tool | Cinder command | Notes |
| --- | --- | --- |
| `kv_get` | `GET key` | Returns `null` when the key is missing |
| `kv_set` | `SET key value [EX s \| PX ms]` | Optional `ex` / `px` TTL |
| `kv_del` | `DEL key` | 1 if the key existed, 0 otherwise |
| `kv_keys` | `KEYS pattern` | Glob `*` and `?`, defaults to `*`. Returns `{"keys": [...], "total": n, "returned": m, "sampled": bool}`: at most `limit` keys (default 100); a larger keyspace returns a deterministic sample seeded by `seed`, and `full: true` returns the whole list |
| `kv_keys_scan` | `SCAN cursor [MATCH pattern] [COUNT n]` | Walk the matching keys one bounded page at a time with cinder's real `SCAN`. Returns `{"keys": [...], "cursor": str, "done": bool, "batch_size": n}`: about `batch_size` keys per page (default 100, max 1000) — `COUNT` is a hint, so a page can run a few keys over when several matches share one hash bucket. Pass the returned `cursor` back for the next page; `""` starts over. When `done` is true the cursor is `""` and the walk is finished. The cursor is opaque: pass it back verbatim. Pages are in `SCAN` order, not sorted; keys added after the cursor are picked up later, keys deleted or renamed between pages can shift the window, and a key can come back twice if the table resizes mid-walk — the same caveats real `SCAN` has |
| `kv_dbsize` | `DBSIZE` | The number of keys in the database; 0 on an empty one. Takes no arguments. One honest detail: cinder's DBSIZE is a maintained counter, so a key whose TTL has passed still counts until a read (or the background expiry scan) reaps it |
| `kv_incr` | `INCR key` / `INCRBY key n` | `by` defaults to 1 |
| `kv_ttl` | `TTL key` | -1 = no expiry, -2 = missing key |
| `kv_pttl` | `PTTL key` | Milliseconds until a key expires; -1 = no expiry, -2 = missing key |
| `kv_exists` | `EXISTS key` | 1 if the key exists, 0 otherwise |
| `kv_expire` | `EXPIRE key seconds` | 1 if the timeout was set, 0 if the key is missing |
| `kv_pexpire` | `PEXPIRE key milliseconds` | 1 if the timeout was set, 0 if the key is missing; milliseconds must be 0 or more |
| `kv_mget` | `MGET key [key ...]` | `keys` is a list of key names; returns the values in the same order, with `null` for a missing key — and for a key holding a non-string, which is real Redis behaviour (unlike `kv_get`, MGET does not fail on a wrong type). At most 1000 keys per call |
| `kv_mset` | `MSET key value [key value ...]` | `values` is an object of key names to values; returns `OK`. Overwrites any type, as in Redis |
| `kv_getdel` | `GETDEL key` | Returns the old value and deletes the key; `null` when the key does not exist |
| `kv_setnx` | `SETNX key value` | 1 if the key was set, 0 if it already existed — whatever it holds, a list or hash counts as existing too |
| `kv_setex` | `SETEX key seconds value` | Returns `OK`; seconds must be more than 0. Overwrites any type, like a plain SET |
| `kv_getset` | `GETSET key value` | Returns the old value, or `null` when the key did not exist; clears the key's TTL, like a plain SET |
| `kv_append` | `APPEND key value` | Appends to a string, creating the key when missing, and returns the new length; preserves the TTL |
| `kv_strlen` | `STRLEN key` | The length of a string; 0 when the key does not exist |
| `kv_decr` | `DECR key` / `DECRBY key n` | `by` defaults to 1 |
| `kv_decrby` | `DECRBY key n` | Decrements by the given amount; creates the key holding `-n` when missing |
| `kv_getex` | `GETEX key [EX s \| PX ms \| PERSIST]` | Returns the value and sets, refreshes, or removes its TTL (`null` when missing; no option leaves the TTL alone) |
| `kv_getrange` | `GETRANGE key start stop` | A substring of a string; negative indices count from the end, out-of-range ends are clamped. `start` defaults to 0, `stop` to -1. `""` when the key does not exist or the range is empty — including a range past the end of a SETRANGE zero-pad, whose zero bytes come back intact |
| `kv_setrange` | `SETRANGE key offset value` | Overwrites a string starting at `offset` and returns the new length; creates the key zero-padded to the offset when missing, extends it when the write runs past the end. Preserves the TTL; an empty value changes nothing and creates nothing (returns the current length, or 0 when missing). The offset must be 0 or more |
| `kv_setbit` | `SETBIT key offset bit` | Sets one bit of a string and returns the bit's old value (0 or 1); the offset must be 0 or more (at most 4294967295) and the bit 0 or 1. Creates the key zero-padded to the byte when missing — even when the bit being set is 0 — and preserves the TTL |
| `kv_getbit` | `GETBIT key offset` | The bit of a string; 0 or 1, and 0 when the key does not exist or the offset is past the end of the string |
| `kv_bitcount` | `BITCOUNT key [start end]` | The number of bits set to 1 in a string; `start` / `end` are byte indexes, both or neither, negative indexes count from the end and out-of-range ends are clamped. 0 when the key does not exist. Cinder has no BYTE\|BIT mode: the range is always in bytes |
| `kv_bitop` | `BITOP AND\|OR\|XOR\|NOT destination key [key ...]` | Combines the strings at several keys bitwise and stores the result; `operation` is `"and"`, `"or"`, `"xor"` or `"not"`, `sources` is the list of source keys. NOT takes exactly one source, the rest take at least two. Returns the length of the destination in bytes; when every source is missing or empty the destination is deleted and 0 is returned. Overwrites the destination wholesale and clears its TTL |
| `kv_bitfield` | `BITFIELD key [GET type offset \| SET type offset value \| INCRBY type offset increment \| OVERFLOW WRAP\|SAT\|FAIL ...]` | Reads and writes packed integer fields of a string; `ops` is a list of subcommands in order (`get` / `set` / `incrby` with a `type` like `"i8"` / `"u8"` and an `offset` as a bit offset or `"#n"` for the n-th field, `overflow` with a `policy` of `"wrap"`, `"sat"` or `"fail"` for the SET / INCRBY ops that follow it). Types are `i1`..`i64` and `u1`..`u63` (no `u64`); a field must end within 2^32 bits. Returns one result per GET / SET / INCRBY, in order: GET the current value (0 past the end or on a missing key), SET the old value, INCRBY the new value, `null` for a SET / INCRBY that overflows under OVERFLOW FAIL. A write creates the key zero-padded and preserves the TTL — even a write that answers `null` under OVERFLOW FAIL leaves the grown string behind, as in Redis |
| `kv_hset` | `HSET key field value [field value ...]` | `fields` is an object of field names to values; returns the number of fields newly added (updating an existing field counts 0) |
| `kv_hget` | `HGET key field` | Returns `null` when the key or the field is missing |
| `kv_hgetall` | `HGETALL key` | Every field as an object of field names to values; `{}` when the key is missing |
| `kv_hdel` | `HDEL key field [field ...]` | `fields` is a list of field names; returns the number of fields actually removed (removing a field that is not present counts 0). Removing the last field deletes the key, as in Redis |
| `kv_hexists` | `HEXISTS key field` | 1 if the field is present in the hash, 0 if it is not or the key does not exist |
| `kv_hlen` | `HLEN key` | The number of fields in the hash; 0 when the key does not exist |
| `kv_hmget` | `HMGET key field [field ...]` | `fields` is a list of field names; returns the values in the same order, with `null` for a field that does not exist — and for every field when the key does not exist |
| `kv_hsetnx` | `HSETNX key field value` | Sets one field only when it does not already exist; 1 if the field was set, 0 if it already existed (the old value is left alone) |
| `kv_hincrby` | `HINCRBY key field increment` | Increments the integer in one field of a hash and returns the new value; creates the field holding the increment when it does not exist, and the key when it does not exist. A negative increment counts down |
| `kv_hscan` | `HSCAN key [MATCH pattern] [COUNT n]` | Walks one hash a bounded page at a time; returns `{"fields": {...}, "cursor": str, "done": bool, "batch_size": n}`; `pattern` matches field names only, cursor passed back verbatim; missing key is done at once with no fields. `COUNT` is exact for `HSCAN`, so a page holds at most `batch_size` fields |
| `kv_hkeys` | `HKEYS key` | The field names of a hash, in cinder's order; at most 1000 fields per call, a larger hash fails instead of returning a truncated list (page it with `kv_hscan` instead). Empty list when the key does not exist |
| `kv_hvals` | `HVALS key` | The values of a hash, in cinder's order, matching `kv_hkeys` field for field; at most 1000 values per call, same cap and missing-key behaviour as `kv_hkeys` |
| `kv_hincrbyfloat` | `HINCRBYFLOAT key field increment` | Increments the float in one field of a hash and returns the new value as a number; creates the field holding the increment when it does not exist, and the key when it does not exist. A negative increment counts down; the increment may be an integer or a float, but not NaN or an infinity; a field holding a non-float fails |
| `kv_hexpire` | `HEXPIRE key seconds [NX \\| XX \\| GT \\| LT] FIELDS numfields field [field ...]` | Sets fields of a hash to expire after a number of seconds; `fields` is a list of field names (at most 1000). Returns one integer per field, in order: -2 the key or the field does not exist, 0 the condition was not met, 1 the expiry was set, 2 the field was deleted at once (a zero TTL). `condition` is `\"nx\"` (only fields with no expiry), `\"xx\"` (only fields that already have one), `\"gt\"` (only when the new expiry is later than the current one) or `\"lt\"` (only when it is sooner); a field with no expiry counts as never expiring, so `gt` never applies to it and `lt` always does. Seconds must be 0 or more |
| `kv_hpexpire` | `HPEXPIRE key milliseconds [NX \\| XX \\| GT \\| LT] FIELDS numfields field [field ...]` | Same as `kv_hexpire` in milliseconds; `milliseconds` must be 0 or more |
| `kv_hexpireat` | `HEXPIREAT key seconds [NX \\| XX \\| GT \\| LT] FIELDS numfields field [field ...]` | Sets fields of a hash to expire at an absolute Unix time in seconds; `fields` is a list of field names (at most 1000). Returns one integer per field, in order: -2 the key or the field does not exist, 0 the condition was not met, 1 the expiry was set, 2 the field was deleted at once (a time already past). Same `condition` options as `kv_hexpire` |
| `kv_hpexpireat` | `HPEXPIREAT key milliseconds [NX \\| XX \\| GT \\| LT] FIELDS numfields field [field ...]` | Same as `kv_hexpireat` in milliseconds |
| `kv_httl` | `HTTL key FIELDS numfields field [field ...]` | Seconds until fields of a hash expire; `fields` is a list of field names (at most 1000). Returns one integer per field, in order: the remaining TTL in seconds, -1 when the field has no expiry, -2 when the key or the field does not exist |
| `kv_hpttl` | `HPTTL key FIELDS numfields field [field ...]` | Milliseconds until fields of a hash expire; same reply shape as `kv_httl` in milliseconds |
| `kv_hpersist` | `HPERSIST key FIELDS numfields field [field ...]` | Removes the expiry from fields of a hash; `fields` is a list of field names (at most 1000). Returns one integer per field, in order: 1 an expiry was removed, -1 the field had no expiry, -2 when the key or the field does not exist |
| `kv_xadd` | `XADD key [MAXLEN [~] threshold] id field value [field value ...]` | Appends one entry to a stream and returns the new entry's ID as a string. `fields` is an object of field names to values (at least one); `id` defaults to `"*"` (auto), `"ms-seq"` is explicit, `"ms-*"` / `"ms-"` takes the millisecond and the next sequence in it — a bare millisecond is not an ID, an explicit `"0-0"` fails, and an ID at or below the stream's top ID fails, while a partial `"0-*"` on an empty stream resolves to `"0-0"`. `maxlen` trims the oldest entries down to that many after the append (`approximate: true` sends `MAXLEN ~`, which cinder trims exactly like the plain form); `maxlen` 0 trims the entry just added, so the key is deleted at once. Creates the stream when it does not exist and preserves its TTL |
| `kv_xrange` | `XRANGE key start end [COUNT count]` | The entries of a stream in an ID range, oldest first, as `[{"id": ..., "fields": {...}}]`. `start` / `end` default to `"-"` / `"+"` (a bare millisecond covers the whole millisecond, `"ms-seq"` is exact), the bounds inclusive. `count` takes at most that many entries (0 answers an empty list); without a count at most 1000 entries are returned and a wider range fails instead of returning a truncated list. Empty list when the key does not exist or the start is past the end. A field named twice in one entry keeps only its last value in the object |
| `kv_xrevrange` | `XREVRANGE key end start [COUNT count]` | The entries of a stream in an ID range, newest first, as `[{"id": ..., "fields": {...}}]`. `end` / `start` default to `"+"` / `"-"` — the bounds are given end-first, as in Redis (a bare millisecond covers the whole millisecond, `"ms-seq"` is exact), the bounds inclusive. `count` takes at most that many entries, highest first (0 answers an empty list); without a count at most 1000 entries are returned and a wider range fails instead of returning a truncated list. Empty list when the key does not exist or the end is below the start. A field named twice in one entry keeps only its last value in the object |
| `kv_xlen` | `XLEN key` | The number of entries in a stream; 0 when the key does not exist |
| `kv_xreadgroup` | `XREADGROUP GROUP group consumer [COUNT count] [BLOCK milliseconds] STREAMS key [key ...] id [id ...]` | Reads a stream as a consumer of a consumer group, as `[{"key": ..., "entries": [{"id": ..., "fields": {...}}]}]` in stream order — streams with nothing new are left out, and a read with nothing new at all answers an empty list. `group` and `consumer` are strings; `streams` is an object of stream keys to IDs (`">"` for the entries after the group's cursor — the new entries, delivered to this consumer and recorded in the group's pending list — or an explicit ID like `"0"` or `"ms-seq"` to re-read this consumer's pending entries after that ID, without changing delivery state; `"$"` is not valid here). `count` takes at most that many entries per stream (1 to 1000); without a count at most 1000 entries per stream are returned and a wider stream fails instead of returning a truncated list. `block` waits up to that many milliseconds for new entries instead of answering at once (1 to 4000: `BLOCK 0` would wait forever, and the socket to cinder times out after 5 seconds, so a longer block would die as a connection error instead of a clean timeout); a block that times out answers an empty list. A blocked read with an explicit ID never wakes on new entries — only entries already pending for this consumer answer it — so it waits out the whole block and answers an empty list when nothing is pending. A missing key or a group that does not exist fails with NOGROUP. Create the group first with `kv_xgroup_create`. At most 100 streams per call |
| `kv_xgroup_create` | `XGROUP CREATE key group id [MKSTREAM]` | Creates a consumer group on a stream and returns `"OK"`. `key` and `group` are strings; `id` is the ID the group starts at (`"$"` by default — only entries added after the group is created, `"0"` for every entry from the beginning, or an explicit ID like `"ms-seq"`). `mkstream: true` creates the stream empty when it does not exist; without it, creating a group on a missing key fails. Creating a group that already exists fails with BUSYGROUP, and a key that is not a stream fails with WRONGTYPE |
| `kv_xack` | `XACK key group id [id ...]` | Acknowledges entries of a consumer group: drops them from the group's pending list and returns how many were dropped. `key` and `group` are strings; `ids` is a list of entry IDs (`"ms-seq"`, at least one, at most 1000). An ID that is not pending counts 0, so acking the same entry twice answers 1 then 0. The entries stay in the stream; only their pending record is dropped. A missing key or a group that does not exist fails with NOGROUP |
| `kv_xclaim` | `XCLAIM key group consumer min-idle-time id [id ...] [IDLE ms] [TIME ms-unix-time] [RETRYCOUNT count] [FORCE] [JUSTID]` | Claims pending entries of a consumer group for another consumer, as `[{"id": ..., "fields": {...}}]` in the order the IDs were given, or only the IDs with `justid: true`. `key`, `group` and `consumer` are strings; `min_idle_ms` is the milliseconds an entry must have been idle since its last delivery (0 claims at once); `ids` is a list of entry IDs (`"ms-seq"`, or a bare millisecond for the first sequence of that millisecond; at least one, at most 1000). An entry that is not in the stream, is not idle enough, or is not pending is left out, and a repeated ID is claimed once. `force: true` claims an entry even when it has not been idle long enough, and claims an entry that is in the stream but not pending at all, creating a pending record for it. `idle_ms` sets the delivery time that many milliseconds ago, or `time_ms` an absolute Unix time in milliseconds — the two cannot be combined. `retrycount` sets the delivery count instead of bumping it by one. A claimed entry moves to this consumer and stays pending until XACK. A missing key or a group that does not exist fails with NOGROUP |
| `kv_xgroup_setid` | `XGROUP SETID key group id` | Moves a consumer group's last-delivered ID and returns `"OK"`. `key` and `group` are strings; `id` is the ID the group moves to (`"$"` by default — the top ID at call time, so the next `">"` read delivers only entries added after it, `"0"` for every entry from the beginning, or an explicit ID like `"ms-seq"`). The next `">"` read delivers the entries after the new ID, and entries already pending stay pending for their consumers — the pending list is untouched. Cinder has no ENTRIESREAD option for SETID, so the tool does not offer it. A missing key or a group that does not exist fails with NOGROUP |
| `kv_xgroup_destroy` | `XGROUP DESTROY key group` | Drops a consumer group and returns 1, or 0 when there was no such group on the stream. `key` and `group` are strings; the group's cursor, consumers and pending list go with it, but the stream and its entries survive, and so do the other groups. A missing key fails with NOGROUP, and a key that is not a stream fails with WRONGTYPE |
| `kv_xpending` | `XPENDING key group [start end count [consumer]]` | The pending entries of a consumer group. With no range arguments it returns the summary as `{"total": ..., "min_id": ... or null, "max_id": ... or null, "consumers": [{"consumer": ..., "count": ...}]}` — the number of pending entries, the lowest and highest pending IDs (null when nothing is pending), and one count per consumer that has anything pending, in the order the consumers first read. Pass `start`, `end` and `count` together for the extended form, which returns one `{"id": ..., "consumer": ..., "idle_ms": ..., "deliveries": ...}` object per pending entry in the ID range, in ID order — the consumer the entry was last delivered to, how many milliseconds since it was last delivered, and how many times it has been delivered; `count` takes at most that many entries (1 to 1000), and `consumer` narrows the list to the entries last delivered to one consumer. A missing key or a group that does not exist fails with NOGROUP. A read, so it changes nothing |
| `kv_xread` | `XREAD [COUNT count] [BLOCK milliseconds] STREAMS key [key ...] id [id ...]` | The entries added to several streams after given IDs, as `[{"key": ..., "entries": [{"id": ..., "fields": {...}}]}]` in stream order — streams with nothing new are left out, and a read with nothing new at all answers an empty list. `streams` is an object of stream keys to IDs (`"$"` for the top ID at read time, so only entries added after the read qualify, `"-"` for every entry, a bare millisecond for the entries after that whole millisecond, or `"ms-seq"`); `">"` is not an ID: use `kv_xreadgroup` for consumer-group reads. `count` takes at most that many entries per stream (1 to 1000); without a count at most 1000 entries per stream are returned and a wider stream fails instead of returning a truncated list. `block` waits up to that many milliseconds for new entries instead of answering at once (1 to 4000: `BLOCK 0` would wait forever, and the socket to cinder times out after 5 seconds, so a longer block would die as a connection error instead of a clean timeout); a block that times out answers an empty list. At most 100 streams per call |
| `kv_zadd` | `ZADD key [NX \| XX \| GT \| LT \| CH \| INCR] score member [score member ...]` | `members` is an object of member names to scores; returns the number of members newly added (updating an existing member's score counts 0), or with `ch: true` the number added or updated. `nx` adds only new members, `xx` updates only existing ones, `gt` only moves a score up, `lt` only moves it down; `nx` cannot combine with `xx`, `gt` or `lt`, and `gt` cannot combine with `lt`. | `kv_zrevrange` | `ZREVRANGE key start stop [WITHSCORES]` | Members in index order, highest score first; negative indices count from the end. `withscores: true` returns `[{"member": ..., "score": ...}]` instead of plain names. At most 1000 members per call |

## Atomic batches

`kv_batch` takes an `atomic` flag (default `false`). With
`atomic: true` the ops run as one `MULTI`/`EXEC` transaction on a
single connection to cinder, so they execute together with no other
client interleaved — a `kv_set` followed by a `kv_incr` on the same
key is one indivisible step. The summary carries `"atomic": true`.

Two honest limits. First, only the single-command ops can be
queued: `kv_keys_scan` cannot run inside a transaction, because its
cursor walk needs one `SCAN` call per page, which cannot happen
inside a transaction. A `kv_xread` or `kv_xreadgroup` with `block` cannot be queued
either: cinder refuses a BLOCK inside `MULTI`/`EXEC` at queue time,
so the whole call fails before anything runs; a plain `kv_xread`
or `kv_xreadgroup` queues and runs at `EXEC` like any other read. Second, queue-time and
EXEC-time failures behave differently, as in real Redis: an op that
cannot be queued at all (unknown name, `kv_keys_scan`, a missing
required argument, a bad `kv_keys` limit) fails the whole call
before anything runs, while an op that fails at EXEC time (an
`INCR` on a non-integer, an `EXPIRE` with a bad time) is recorded
in place as that op's error and the rest still run. `kv_keys`
inside an atomic batch returns the same sampled shape as the
standalone tool.

| `key-migration` | `pattern` (optional, defaults to `*`), `target_prefix` (required), `max_keys` (optional, safety cap, defaults to 20, at most 100) | Plans migrating keys to a new prefix: audits each key's type, size, and TTL, checks whether the target name already exists and with what type, and lays out the ordered copy steps with the exact `kv_del` call for each source key — except list keys, which move atomically one element at a time with `kv_lmove` (from `'left'` to `'right'`, once per element, in order; the last move deletes the source, so no `kv_del`, and the TTL is re-applied with `kv_expire` since `LMOVE` creates the target with no expiry; a move interrupted halfway is safe to resume). A self-mapped list key needs no move at all — `kv_lmove` with source and destination the same key would rotate the list. An overwrite list key says to delete the target first, since `kv_lmove` would otherwise append onto its existing list — ready keys (free target), overwrite keys (target exists, same type), conflicts (target exists, different type), keys that map onto themselves, and keys that expired mid-scan. Values are never read or printed. One honest limit: cinder has no RENAME or COPY, so a migration of a non-list key is a read plus a write, not one atomic move — the plan says to verify the target before deleting the source, and to re-check the TTL with `kv_ttl` just before copying since the audited TTL ticks down |

Fetchable with `prompts/list` and `prompts/get`.

## Streaming the keyspace

`ttl-audit`, `cleanup-plan`, `keyspace-health`, `ttl-renewal`, and
`key-migration` scan the keyspace in bounded batches
of 100 keys (`cinder_mcp/scan.py`), and `kv_keys_scan` exposes the
same walk as a paged tool. The per-key work and the prompt text stay
bounded: the prompts keep only counts plus the 10 soonest-expiring
keys, the first 20 no-expiry keys, and the first 20 keys per cleanup
section, with "... and N more" for the rest. The results are
identical to the old load-everything scan at any batch size — the
tests run the scanning prompts at batch sizes 1, 2, 7 and 100 over the same
keyspace and compare the full prompt text.

The scanner is backed by cinder's real `SCAN` command (cinder
0.26.0): `SCAN cursor [MATCH pattern] [COUNT n]` returns
`[cursor, keys]`, and the walk repeats with the returned cursor
until it comes back `0`. The tools and prompts did not change —
only `cinder_mcp/scan.py` did. Two honest details: `COUNT` is a
hint, so a page can run a few keys over `batch_size` when several
matches share one hash bucket, and real `SCAN` may return a key
twice if the table resizes mid-walk, so the prompt iterator
dedupes against a seen set while `kv_keys_scan` exposes the raw
paged walk, duplicates included. Pages are in `SCAN` order, not
sorted key order.
